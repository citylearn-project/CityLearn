# KPIs Reference

The simulator exposes two KPI APIs.

| API | Status | Format | Recommended use |
|---|---|---|---|
| `evaluate()` | legacy | DataFrame with historical cost-function names | Compatibility with older workflows. |
| `evaluate_v2()` | primary | DataFrame with structured KPI names | Production, dashboards and scientific comparison. |

For the full v2 naming tree, see [KPI_V2_TREE.md](KPI_V2_TREE.md).

Start with [How to read the scorecard](scorecard.md) for a compact selection,
baseline interpretation and an executable table-selection example. The `v2`
method name denotes the KPI interface, not CityLearn version 2.

To list the exact names available in your own configured run:

```python
kpis = env.evaluate_v2()
catalogue = kpis[["cost_function", "level"]].drop_duplicates().sort_values("cost_function")
print(catalogue.to_string(index=False))
```

Feature-specific KPI availability follows the schema. A missing/undefined value
is not a zero measurement; preserve it when exporting or comparing.

## KPI v2 Naming Contract

```text
level_family_subfamily_metric_variant_unit
```

| Part | Examples |
|---|---|
| `level` | `building`, `district`. |
| `family` | `cost`, `energy_grid`, `emissions`, `solar_self_consumption`, `ev`, `battery`, `electrical_service_phase`, `equity`, `comfort_resilience`, `deferrable_appliance`, `escalator`, `demand_response`, `robustness`. |
| `subfamily` | `total`, `daily_average`, `ratio_to_baseline`, `ratio_to_business_as_usual`, `shape_quality`, `service`. |
| `metric` | `import`, `export`, `charge`, `completed_cycles`. |
| `variant` | `control`, `baseline`, `business_as_usual`, `delta`, `delta_to_business_as_usual`, `total`, `average`, `l1`. |
| `unit` | `eur`, `kwh`, `ratio`, etc. |

Examples:

| KPI | Meaning |
|---|---|
| `district_cost_total_control_eur` | Total control cost. |
| `district_cost_total_business_as_usual_eur` | Total native business-as-usual baseline cost. |
| `building_energy_grid_total_import_control_kwh` | Building import energy. |
| `building_energy_grid_ratio_to_business_as_usual_import_total_ratio` | Building import relative to the native business-as-usual baseline. |
| `district_energy_grid_shape_quality_ramping_average_to_baseline_ratio` | Ramping relative to baseline. |
| `district_solar_self_consumption_ratio_self_consumption_ratio` | District/community solar self-consumption ratio after same-timestep member imports and exports are balanced. |
| `building_deferrable_appliance_service_completed_cycles_count` | Completed deferrable cycles. |
| `building_escalator_service_service_level_ratio` | Passenger demand served by escalators. |
| `district_demand_response_compliance_ratio` | Credited DR delivery divided by valid requested energy. |
| `district_robustness_action_dropout_count` | Number of action dropouts applied by robustness events. |

## Core Equations

For net energy `net_t`, where import is positive and export is negative:

```text
total_import_kwh = sum(max(net_t, 0))
total_export_kwh = sum(max(-net_t, 0))
total_net_exchange_kwh = sum(net_t)
daily_average_x = total_x / simulated_days
delta_x = control_x - baseline_x
ratio_to_baseline_x = control_x / baseline_x
delta_to_business_as_usual_x = control_x - business_as_usual_x
ratio_to_business_as_usual_x = control_x / business_as_usual_x
self_consumption = (solar_generation_total - export_total) / solar_generation_total
```

District ratios divide district totals: `district_..._ratio_to_baseline_x` is
the district control total over the district baseline total, like every
`ratio_to_business_as_usual` ratio. A mean of building ratios is not a district
ratio; the legacy `evaluate()` API keeps that mean as its district row, and
`evaluate_v2()` publishes it under the `building_mean` variant (see
[Definitions changed after 3.6.0](#definitions-changed-after-360)).

District emissions are the emissions of the district grid import,
`max(sum_members(net_t), 0)` at each step, so energy that one member exports and
another imports in the same step carries no grid carbon. Each imported kWh is
charged at the carbon intensity of the member that imports it; when importing
members have different intensities, the locally covered share of each import
follows the weighted allocation of the energy provenance ledger, and the
control total equals `district_energy_provenance_external_purchase_emissions_kgco2`.
Building emissions are each member's own import times its carbon intensity, so
they do not add up to the district total when members share energy.

Safe division returns `None` (undefined) when the control or the reference is
missing or not finite; an undefined value is never read as zero. For a reference
within the numerical zero tolerance it returns `1.0` ("no change") if the
control is also effectively zero, and `None` otherwise. The
deferrable-appliance service ratios to the BAU are the exception: when no cycle
was due in either run (both totals zero) they are undefined.

Ratios stay lower-is-better when the reference total is negative. Net exchange
(legacy `zero_net_energy`) and cost totals can be negative, for a net exporter
or after community-market revenue. Their ratios to the baseline and to BAU use

```text
ratio_x = control_x / reference_x                        if reference_x > 0
ratio_x = 1 + (control_x - reference_x) / |reference_x|  if reference_x < 0
```

so 1 still means no change and a higher control total gives a higher ratio.
For a positive reference this is the plain ratio. Import, export and emission
totals are never negative and use the plain ratio.

Grid-shape KPIs work on power, `net_t / step_hours`:

```text
load_factor_penalty = mean over windows of (1 - mean(import_w) / max(import_w))
ramping_average     = sum_t max(net_t - net_(t-1), 0) / transitions
```

with `import = max(net, 0)` and daily (24 h) or monthly (730 h) windows. A
window whose peak import is zero has no load factor and is left out of the mean;
the KPI is undefined when no window is defined. `ramping_average` is a mean per
step transition, so it does not grow with the episode length.

The conventional `baseline` counterfactual follows the grid outage of the
controlled run: at power-outage time steps the `*_without_storage*` net series,
and their cost and emission series, are zero. Neither run exchanges energy with
the grid while it is down.

## EV KPIs

| Concept | Unit | Meaning |
|---|---:|---|
| departure count | count | Number of EV departures observed. |
| departure met count | count | Departures where required SOC was met. |
| departure minimum acceptable count | count | Departures where SOC is at least `target_soc - ev_departure_service_tolerance`. |
| departure within tolerance count | count | Departures within the configured symmetric target tolerance. |
| departure target feasible/infeasible count | count | Departures where the strict target SOC was/was not reachable by charging at max power for the connected interval, after charger/battery efficiency and configured electrical-service headroom. |
| departure minimum acceptable feasible/infeasible count | count | Departures where the minimum acceptable SOC was/was not reachable under the same max-power, efficiency and electrical-service constraints. |
| departure within tolerance feasible/infeasible count | count | Departures where the lower bound of the symmetric tolerance band was/was not reachable under the same max-power, efficiency and electrical-service constraints. |
| departure success ratio | ratio | `met / departures`. |
| departure minimum acceptable ratio | ratio | `minimum_acceptable / departures`. This is the main user-service comfort KPI. |
| departure within tolerance ratio | ratio | `within_symmetric_tolerance / departures`. |
| departure success feasible ratio | ratio | Strict target fulfillment over feasible strict-target departures only. |
| departure minimum acceptable feasible ratio | ratio | Minimum service fulfillment over feasible minimum-service departures only. This is the main controller-quality KPI. |
| departure within tolerance feasible ratio | ratio | Symmetric target accuracy over feasible within-tolerance departures only. |
| departure SOC deficit mean | ratio | Mean non-negative SOC deficit over departures. |
| departure shortfall beyond tolerance mean | ratio | Mean deficit below `target_soc - ev_departure_service_tolerance`. |
| departure SOC surplus mean | ratio | Mean non-negative SOC surplus over departures. |
| departure SOC absolute error mean | ratio | Mean absolute SOC error to the requested target. |
| departure tolerance | ratio | Configured service tolerance used for minimum acceptable departure SOC. |
| charge total | kWh | Energy charged into EVs. |
| V2G export total | kWh | Energy exported by EVs. |

EV departure tolerance semantics:

- `ev_departure_success_rate` is strict target fulfillment: `actual_soc >= target_soc`.
- `ev_departure_min_acceptable_rate` is minimum service fulfillment: `actual_soc >= target_soc - ev_departure_service_tolerance`.
- `ev_departure_within_tolerance_rate` is symmetric target accuracy: `abs(actual_soc - target_soc) <= ev_departure_within_tolerance`.
- The `*_feasible_rate` variants use the same numerators but exclude departures where that threshold was not physically reachable from arrival SOC by charging at maximum charger/battery power for the connected interval, capped by configured building/phase import headroom and charger/battery efficiency.
- Feasibility counters are scenario-quality diagnostics; missing charger, battery or arrival-SOC data is treated as feasible to preserve legacy dataset behavior.
- Both tolerance settings default to `0.05`.

## Deferrable Appliance KPIs

| Concept | Unit | Meaning |
|---|---:|---|
| completed cycles | count | Cycles completed successfully. |
| missed cycles | count | Cycles that missed the start window. |
| service level | ratio | `completed / (completed + missed)`. |
| served energy | kWh | Energy of completed cycles. |
| unserved energy | kWh | Energy of missed cycles. |
| average start delay | hours | Mean `start - earliest_start` over completed cycles; undefined when no cycle completed. |

Service level and average start delay are undefined, not 0 or 1, in windows
where no cycle was due or none completed; so are their deltas and ratios to the
BAU. Preserve the missing values when exporting or comparing.

## Demand Response KPIs

Available when `demand_response.enabled=true`.

| KPI suffix | Level | Unit | Meaning |
|---|---|---:|---|
| `demand_response_events_count` | building/district | count | Unique DR events with active settlement rows. |
| `demand_response_active_time_step_count` | building/district | count | Number of active DR timesteps. |
| `demand_response_requested_total_kwh` | building/district | kWh | Requested energy from `target_power_kw` over active steps. |
| `demand_response_delivered_total_kwh` | building/district | kWh | Signed delivery, positive when the controller moves in the requested direction. |
| `demand_response_shortfall_total_kwh` | building/district | kWh | Non-delivered requested energy after tolerance. |
| `demand_response_compliance_ratio` | building/district | ratio | Credited delivery divided by valid requested energy. |
| `demand_response_revenue_total_eur` | building/district | eur | Credited delivery revenue. |
| `demand_response_penalty_total_eur` | building/district | eur | Shortfall penalty. |
| `demand_response_net_revenue_total_eur` | building/district | eur | Revenue minus penalty. |
| `demand_response_invalid_baseline_time_step_count` | building/district | count | Active steps excluded from economics because the pre-event baseline was invalid. |
| `demand_response_uncapped_contribution_total_kwh` | building | kWh | Diagnostic: the member's own positive contribution, without the district tolerance and cap. Does not add up to the district. |

Names are prefixed with `district_` or `building_`, for example `district_demand_response_net_revenue_total_eur`.

Building rows split the district settlement of each step. The request is split
equally over the active members. The district credited energy and revenue are
allocated by the revenue weights (each member's share of the positive
contributions), and the district shortfall and penalty by the penalty weights
(each member's share of the negative contributions, otherwise of the pre-event
baseline). Building credited energy, shortfall, delivery, revenue and penalty
therefore add up to the district values and respect the district tolerance and
the cap at the target. A building's compliance is its credited energy over its
equal share of the request, capped at 1, so the mean of the building compliance
ratios never exceeds the district ratio.

## Definitions changed after 3.6.0

The KPI definition version (`kpi_definition_version` in the
`energy_accounting` metadata of `evaluate_v2()`) is `2.0.0`. These rows of
`evaluate_v2()` changed definition. Where a 3.6.0 value may have been used in
published comparisons, it is kept under a distinct name, and the legacy
`evaluate()` rows keep their own 3.6.0 definitions.

| KPI | New definition | 3.6.0 value kept as |
|---|---|---|
| `district_energy_grid_ratio_to_baseline_import_total_ratio` | District import total over district baseline total. | `district_energy_grid_ratio_to_baseline_import_total_building_mean_ratio`; legacy `electricity_consumption_total` |
| `district_energy_grid_ratio_to_baseline_net_exchange_total_ratio` | Signed ratio of the district net-exchange totals. | `district_energy_grid_ratio_to_baseline_net_exchange_total_building_mean_ratio`; legacy `zero_net_energy` |
| `district_emissions_ratio_to_baseline_total_ratio` | District emissions total over district baseline total. | `district_emissions_ratio_to_baseline_total_building_mean_ratio`; legacy `carbon_emissions_total` |
| `district_emissions_total_{control,baseline,business_as_usual}_kgco2` and their deltas, daily averages and ratios | Emissions of the netted district import. | `district_emissions_total_{control,baseline,business_as_usual}_member_sum_kgco2` |
| `district_energy_grid_shape_quality_load_factor_penalty_{daily,monthly}_average_to_baseline_ratio` | Load factor of import power; windows without import are undefined. | `..._to_baseline_signed_net_ratio`; legacy `daily_one_minus_load_factor_average`, `monthly_one_minus_load_factor_average` |
| `district_energy_grid_shape_quality_load_factor_penalty_{daily,monthly}_average_{business_as_usual,delta_to_business_as_usual}_ratio`, `..._to_business_as_usual_ratio` | As above. | `district_energy_grid_shape_quality_load_factor_penalty_{daily,monthly}_average_signed_net_*` |
| `district_energy_grid_shape_quality_ramping_average_{business_as_usual,delta_to_business_as_usual}_kw` | Mean upward ramp per step transition. The ratio to the BAU is unchanged. | `district_energy_grid_shape_quality_ramping_total_{business_as_usual,delta_to_business_as_usual}_kw` |
| `*_deferrable_appliance_service_average_start_delay_hours` | Undefined when no cycle completed (was 0). | none |
| Ratios with an undefined control or reference | Undefined (were read as 0, or 1 when both were undefined). | none |
| `*_deferrable_appliance_ratio_to_business_as_usual_*_ratio` with both totals zero | Undefined (was 1). | none |
| `building_demand_response_{shortfall_total_kwh,compliance_ratio}` | Allocated from the district settlement. | `building_demand_response_uncapped_contribution_total_kwh` (diagnostic) |
| Portfolio EV departure rates and means, deferrable and escalator service levels, start delay and solar self-consumption (`MultiCommunityEnv`) | Pooled from their additive denominators. | none |

In the legacy rows, a load-factor window whose signed peak is not positive is
now undefined; it used to give an infinite or negative penalty, which safe
division reported as a perfect 0.
