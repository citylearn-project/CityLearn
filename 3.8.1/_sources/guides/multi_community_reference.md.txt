# Multi-Community Reference

`MultiCommunityEnv` orchestrates several independent `CityLearnEnv` instances with one child environment per community. V1 is synchronization and portfolio reporting only: there is no global physics layer, inter-community market, global DSO/TSO coordination or building mixing across communities.

## Quickstart

```python
import numpy as np
from citylearn.multi_community import MultiCommunityEnv

env = MultiCommunityEnv(
    communities=[
        {
            "community_id": "community_a",
            "schema": "citylearn_challenge_2022_phase_all_plus_evs",
            "env_kwargs": {"interface": "entity", "episode_time_steps": 48},
            "weight": 1.0,
        },
        {
            "community_id": "community_b",
            "schema": "citylearn_challenge_2022_phase_all",
            "env_kwargs": {"interface": "entity", "episode_time_steps": 48},
            "weight": 2.0,
        },
    ],
    render_directory="outputs/runs",
    render_session_name="portfolio_001",
)

observations, info = env.reset(seed=0)
terminated = truncated = False

while not (terminated or truncated):
    actions = {
        community_id: {
            "tables": {
                table: np.zeros(space.shape, dtype="float32")
                for table, space in child.action_space["tables"].items()
            }
        }
        for community_id, child in env.envs.items()
    }
    observations, rewards, terminated, truncated, info = env.step(actions)

kpis = env.evaluate_v2(include_business_as_usual=False)
print(kpis.loc[kpis["level"] == "portfolio"].head())
env.close()
```

## Constructor

```python
MultiCommunityEnv(
    communities=[
        {
            "community_id": "community_a",
            "schema": "path/or/dataset/name/schema.json",
            "env_kwargs": {"interface": "entity", "episode_time_steps": 48},
            "weight": 1.0,
        }
    ],
    render_directory=None,
    render_session_name=None,
)
```

`community_id` must be unique, non-empty and safe as a relative path component. It may contain only letters, numbers, `_`, `-` and `.`. `weight` defaults to `1.0`, must be finite and non-negative, and at least one community must have a positive weight. Only `community_id`, `schema`, `env_kwargs` and `weight` are accepted in an entry: any other key raises a `ValueError` that names it, and `weight` must be a number: a boolean or a string such as `'2'` raises a `ValueError`.

`env_kwargs` are passed to the child `CityLearnEnv`. The wrapper sets each child export session to `<render_session_name>/<community_id>` so render and KPI files are separated by community.

## Reset And Step

`reset()` returns child observations by community plus wrapper info:

```python
observations = {"community_a": child_observations, "community_b": child_observations}
info = {"communities": {...}, "time_step": 0}
```

`reset(seed=..., options=...)` passes `seed` to every child. `options` can hold one
mapping per community, keyed by `community_id`; a community without its own entry
receives the whole `options` mapping:

```python
# community_a replays episode 2. community_b has no entry, so it receives the
# whole mapping and replays episode 0.
env.reset(options={"community_a": {"episode_index": 2}, "episode_index": 0})

# The same options for every child.
env.reset(options={"episode_index": 2})
```

`step(actions)` expects one child action payload per community:

```python
actions = {"community_a": child_actions, "community_b": child_actions}
```

It returns:

```python
observations_by_community,
rewards_by_community,
terminated,
truncated,
info
```

`info` includes:

| Key | Meaning |
|---|---|
| `community_rewards_scalar` | Finite sum of each child reward payload. |
| `reward_total` | `sum(weight * community_reward_scalar)`. |
| `reward_mean_weighted` | `reward_total / sum(weights)`. |
| `terminated_by_community` | Child termination flags. |
| `truncated_by_community` | Child truncation flags. |

If any child terminates or truncates, the wrapper terminates or truncates too. This prevents the communities from drifting into different episode positions.

## Synchronization Contract

All child environments must use:

| Requirement | Reason |
|---|---|
| Same `seconds_per_time_step` | Keeps step time aligned. |
| Same effective episode length | Keeps training batches rectangular. |
| Same `interface` | Keeps observation/action payload contracts stable. |
| Same `central_agent` mode | Avoids mixing centralized and decentralized reward/action semantics. |
| Same `physics_version` | Portfolio totals add up district values, so every community must simulate the same physics. |
| Same `random_stream_version` | Randomly drawn defaults (battery curves, efficiencies, noise) must come from the same stream definition for the totals to be comparable. |
| Same `baseline_version` | Portfolio baseline KPIs add up district baselines, so the baseline definition must match. |
| Same `business_as_usual_ev_charge_target` | Portfolio BAU totals and ratios to the BAU add up the district BAU runs, so every community must charge its EVs in the BAU to the same target (`full` or `requested`). |
| Same `ev_soc_carryover` | It changes the EV state at the start of each episode in the controlled and BAU runs, so portfolio totals would otherwise mix two EV definitions. |
| Same `ev_departure_service_tolerance` and `ev_departure_within_tolerance` | They set the min-acceptable and within-tolerance thresholds of the EV departure counts that the portfolio adds up. |
| Same `energy_provenance` | A community with the provenance ledger off has no provenance rows, so the portfolio provenance totals would cover only the other communities. |
| Same `evaluation_window` when enabled | Keeps recurring window KPIs aligned across communities. |

The wrapper validates these conditions at construction and again after reset, and
raises a `ValueError` that names the setting, for example:

```text
ValueError: MultiCommunityEnv requires all communities to share business_as_usual_ev_charge_target, got {'A': 'full', 'B': 'requested'}.
```

Each community draws its own random values. The wrapper passes its `community_id` to the child as
`random_stream_namespace`, which is added to the key of every random stream (drawn device parameters, EV
drift and initial SOC, occupant interactions, stochastic outages, data and robustness noise). Two communities
with the same seed and the same building or EV names, such as `pt_rec_4` and `pt_rec_15`, therefore draw
independent values, while the shared seed still selects the same episode windows. A community's draws differ
from those of the same dataset run alone as a `CityLearnEnv`; pass the same `random_stream_namespace` in
`env_kwargs` to the standalone environment to reproduce them. `compare_manifests()` reports two runs with
different namespaces as incompatible (`random_stream_namespace`)
([#462](https://github.com/citylearn-project/CityLearn/issues/462)).

Calendar windows are not part of the contract. Each child selects its episode
split from its own simulation window, `random_episode_split` setting and
`random_seed`, so communities can simulate different dates at the same step.
To share windows, give the children the same window settings and the same
`random_seed`, or pass a seed to `reset(seed=...)`, which reaches every child.

## Demand Response

Demand response remains local to each community. If a child schema has `demand_response.enabled=true`, that child loads its own `requests_file`, exposes its own request metadata in entity observations, and computes local settlement/KPIs. `MultiCommunityEnv` does not coordinate DSO/TSO requests across communities in v1.

## KPI Aggregation

`evaluate_v2()` concatenates the child KPI tables and adds a `community_id` column. It also adds portfolio rows:

```text
level = "portfolio"
name = "Portfolio"
community_id = "__portfolio__"
```

Only district-level child KPIs are aggregated:

| KPI suffix | Portfolio rule |
|---|---|
| `_kwh`, `_eur`, `_kgco2`, other `_count` | Sum across communities. |
| `_ratio` of a control total to a reference total | Ratio of the summed totals, e.g. `portfolio_cost_total_control_eur / portfolio_cost_total_baseline_eur`. |
| Rates and means with additive denominators | Pooled: mean weighted by the denominator, e.g. `portfolio_ev_events_departure_met_count / portfolio_ev_events_departure_count`. |
| `energy_provenance_{storage,bus}_max_residual_kwh` and their BAU values | Largest community value; the delta to the BAU is the difference of the two portfolio maxima. |
| Other `_ratio`, `_percent` | Weighted mean using community `weight`. |
| `energy_grid_window_average_power_*_kw` | Signed sum across communities sharing `evaluation_window` (`NaN` if any community value is undefined). |
| Other `_kw`, `_c`, other `_hours` and other point metrics | Not aggregated in v1. |

Ratios rebuilt from summed totals are the `ratio_to_baseline` and
`ratio_to_business_as_usual` ratios of cost, emissions, grid import, export and
net exchange, and the `ratio_to_business_as_usual` ratios of solar generation
and export, EV charge and V2G export, battery charge, discharge and throughput,
and deferrable-appliance cycle and energy counts. They use only communities that
report both totals, ignore `weight` like the summed totals, and keep the
lower-is-better rule of the [KPI reference](kpis_reference.md#shared-rules)
for negative net-exchange and cost totals. A one-community portfolio ratio
equals the district ratio.

Pooled rates and means are weighted by their additive denominators, so they
equal the ratio of the pooled numerator and denominator and ignore `weight`:

| Rate or mean | Weight |
|---|---|
| EV departure success, minimum-acceptable and within-tolerance rates; SOC deficit, shortfall, surplus and absolute-error means | `ev_events_departure_count` |
| EV `*_feasible` departure rates | The matching `ev_events_departure_*_feasible_count` |
| Deferrable-appliance service level (control and BAU) | Completed plus missed cycles |
| Deferrable-appliance average start delay (control and BAU) | Completed cycles |
| Escalator service level | Requested passengers |
| Solar self-consumption (control and BAU) | Solar generation |
| Community-market local share of demand (`*_local_share_of_demand_ratio`, `*_import_share_ratio`) | Local import plus grid import after local trading |
| Community-market local share of export | Local export plus grid export after local trading |
| Demand-response compliance | `demand_response_valid_requested_total_kwh` |
| Demand-response audit compliance, requested-energy coverage and baseline coverage, per purpose | The audit's valid requested energy, requested energy and active intervals |
| Stationary-battery equivalent full cycles and capacity fade (control and BAU) | Nominal stationary-battery capacity |
| EV departure audit: service coverage and threshold coverage (`ev_departure_audit_*coverage_ratio`) | `ev_departure_audit_departures_count` |
| EV departure audit: `*_service_observed_ratio` | `ev_departure_audit_service_observed_count` |
| EV departure audit: `*_service_feasible_ratio` | The matching `ev_departure_audit_*_feasible_service_observed_count` |
| Thermal-service audit: discomfort, thermal coverage and their outage variants | Evaluated occupied, occupied, evaluated outage occupied and outage occupied intervals |
| Thermal-service audit: occupancy and energy coverage | Executed intervals |
| Thermal-service audit: unserved service ratio and its outage variant | Expected service energy, over all intervals or outage intervals |
| Flexible-appliance audit: observed completion and resolved coverage; resolved completion | Offered requests; resolved requests |
| Equity audit: coverage ratio; losers percentage | Population members; eligible members |
| Useful PV (`energy_provenance_pv_useful_{building,with_mobility}_ratio`, control and BAU) | `energy_provenance_pv_generated_kwh` (control or BAU) |

The BAU deltas and ratios of the pooled deferrable service level, start delay,
self-consumption, equivalent full cycles, capacity fade and useful PV compare the
pooled control and BAU values. Communities whose value is undefined carry no weight.
Communities with weight 0 still count in these rows, as in the summed totals: a
pooled rate is the rate of the portfolio's own counts
([#428](https://github.com/citylearn-project/CityLearn/issues/428)).

For stationary batteries, the portfolio cycle count is total throughput divided
by twice the total nominal capacity, and the capacity fade is the capacity lost
over the total nominal capacity. Installed batteries contribute their capacity
even if they are idle. The result is undefined when the total capacity is zero.

Ratios without additive totals stay means weighted by the community `weight`:

| Rows | Why they are not pooled |
|---|---|
| Grid-shape ratios (peaks, ramping and load-factor penalties) | A portfolio peak or load factor needs the summed time series, which the district rows do not hold. |
| Equity Gini, top-20 % share and asset-poor over asset-rich ratio | Distributions over the members; they cannot be rebuilt from district counts. |
| Legacy comfort and resilience rows (`comfort_resilience_*`) and the legacy equity losers percentage | Their district values are plain means of the buildings; the pooled canonical rows are the thermal-service and equity audits. |
| `*_building_mean_ratio` rows | Means of member ratios by definition. |
| Phase imbalance and the EV departure tolerance | A time average of imbalance, and a setting that every community shares. |

Each portfolio row has its own `description`, which states its rule and then the
district definition, for example `Portfolio: pooled over the communities: their
values weighted by portfolio_ev_departure_audit_departures_count, ...`. The export
manifest lists the rule of every row under `portfolio_aggregation`.

Communities without a community market report zeros in their market rows. In a
portfolio where some communities have a market and others do not, a community
without a market enters the portfolio market rows
(`portfolio_energy_grid_community_market_*`, `portfolio_cost_community_market_*`
and `portfolio_solar_self_consumption_community_market_*`) with its plain grid
settlement: no local trade, its members' grid import and export as grid import
and export after local trading, its `cost_total_control_eur` as settled and
counterfactual cost, and zero savings and operator balance. The portfolio
market rows then cover every community, and the shares are those of the whole
portfolio. The community's own district rows do not change, and neither do
portfolios where every community has a market or none has
([#373](https://github.com/citylearn-project/CityLearn/issues/373)).

Portfolio KPI names replace a leading `district_` prefix with `portfolio_`, for example `district_demand_response_revenue_total_eur` becomes `portfolio_demand_response_revenue_total_eur`.

## Scorecard

`scorecard(kpis=None, level=None, **evaluate_kwargs)` returns the rows of
`CityLearnEnv.SCORECARD_DEFAULT_KPIS` for every community and, with `portfolio_`
in place of `district_`, for the portfolio. Rows follow that list, then the
communities in order, with the portfolio last. `level` keeps only `'portfolio'`,
`'district'` or `'building'` rows.

## Export

`export_final_kpis()` writes each child export in its own subfolder and writes the portfolio table and its manifest in the wrapper session folder:

```text
<render_directory>/<render_session_name>/
  exported_kpis_multi_community.csv
  exported_kpis_multi_community.manifest.json
  community_a/exported_kpis.csv
  community_a/exported_kpis.manifest.json
  community_b/exported_kpis.csv
  community_b/exported_kpis.manifest.json
```

The portfolio table keeps the long `evaluate_v2()` format with local and portfolio
rows and the `unit`, `description`, `status` and `replacement` columns. It is
written as `exported_kpis_multi_community.parquet` when every community uses
`render_file_format="parquet"`. Each child keeps its wide numeric table and stores
its KPI definitions in `exported_kpis.manifest.json`.
`include_battery_health_audit=True` adds the opt-in EV battery-health rows to every
table, as in `evaluate_v2()`.

The portfolio manifest records:

| Key | Content |
|---|---|
| `kind`, `definition_version` | `"multi_community"` and the manifest version. |
| `community_ids`, `weights` | The communities in order and their weights. |
| `shared_settings` | The settings every community shares (interface, step, episode length, evaluation window, physics, random-stream and baseline versions, BAU EV target, EV tolerances, SOC carry-over, energy provenance). |
| `kpi_export` | `include_business_as_usual`, `include_battery_health_audit`, `kpi_round_decimals`, whether the community tables were written, and the file format. |
| `controller_identity` | The identity set with `set_experiment_identity()`. |
| `portfolio_aggregation` | The rule of each portfolio row and the rows it is built from. |
| `kpi_definitions` | Unit, description, status and replacement of every KPI in the table, portfolio rows included. |
| `communities` | For each community: its weight, random-stream namespace, the path of its manifest relative to the session folder, and the evidence that `compare_manifests()` reads. |

`set_experiment_identity(implementation, version, parameters, observation_access)`
declares the controller of every community at once. `compare_exports()` on two
portfolio tables reads their manifests: the portfolios pair when they have the
same communities, weights and portfolio rules and each community pairs with its
namesake; a community's mismatches and missing evidence are listed as
`<community_id>:<item>`, for example `community_a:controller_identity`
([#429](https://github.com/citylearn-project/CityLearn/issues/429)).
